Engelbart · launch diagnostics

Why these two projects stopped

Two different runner limitations: package-manager support in Manifund, and repository-wide container gating in OpenScience.

Explanation only · no fixes implemented

01 · Manifund

Stopped during dependency installation

npm rejected the dependency tree. The runner then rejected the proposed workaround.

  1. The first port conflict was handled. Port 3000 was occupied. Repair selected port 61671 and updated the Next.js launch arguments and health URL. The app had not started yet.
  2. Installation failed with ERESOLVE. The app pins react@19.2.5. npm selected @headlessui/react@1.7.19, whose declared React peer range is ^16 || ^17 || ^18. React 19 falls outside that range.
  3. Repair proposed npm install --legacy-peer-deps. The runner permits plain npm install/ci, but does not permit this flag. The validator rejected the proposal before it executed.
  4. The agent returned unsupported on attempt 3. Five attempts is a maximum, not a requirement to keep retrying after the agent reports no supported plan.
The repository’s own README says to use bun install and bun run dev. The assessed plan used npm instead.

This is a package-manager selection and capability gap in the runner, alongside a real declared dependency mismatch. The logs do not establish that the app itself cannot run. They also do not establish that Bun or ignoring peer checks would produce a working app.

What a future fix should address

  • Detect the documented package manager, its manifest declaration, and lockfile before choosing installation commands.
  • Support bounded Bun install/run commands and check whether the required runtime is available.
  • If an npm peer-dependency override is supported later, treat it as a compatibility workaround and verify the resulting app. Ignoring a peer range does not repair the underlying compatibility contract.
This failure was not caused by environment variables. Installation stopped before application startup. Missing app configuration may still become a separate blocker afterward.
Evidence and diagnostic limitations
  • User-provided install log: ERESOLVE unable to resolve dependency tree, React 19.2.5 and Headless UI 1.7.19.
  • User-provided repair trace: attempt 2 proposed --legacy-peer-deps; the host rejected it as outside supported setup operations.
  • User-provided README excerpt: steps 2–5 specify Bun and its install/run commands.
  • The agent’s claim that the conflict “can only” be resolved with npm flags or edits is too broad; it omits the repository’s documented package-manager workflow.
  • originalFailure contains an empty initial “plan” state in this trace. Failure context should track the real execution blocker as it changes, while retaining earlier failures.

02 · OpenScience

Stopped before assessment

A container test fixture triggered a global stop before any model call or launch attempt.

  1. Discovery found a Compose service at tooling/harbor/native-smoke/task/environment/docker-compose.yaml#main.
  2. The host checked every discovered component. In project_order.py, any component with requiresContainer causes the entire assessment to stop.
  3. No agent ran. This explains the displayed 0 model calls. The agent never had an opportunity to select the intended app or exclude unrelated tooling.
“Declared container services need a container-capable runtime. Native startup will not be inferred over them.”

The fixture README explicitly describes a small Harbor compatibility test using a Docker task environment. Its Compose service runs sleep infinity with networking disabled. That is evidence about the test fixture, not proof that the default application requires Docker.

What a future fix should address

  • Let assessment classify and exclude test fixtures before enforcing runtime requirements.
  • Require container support when a selected service needs it, rather than whenever any Compose file exists in the repository.
  • Preserve container requirements for services actually chosen; do not invent native replacements.
Removing this gate alone would not guarantee a launch. Local discovery found 17 components, exceeding the next host check’s six-component limit. The root declares bun@1.3.14; its default dev launches a CLI, while dev:ui targets the workspace frontend. Component selection, Bun support, and the intended preview entry point still need assessment.
Locally checked evidence
  • Runner: hc/src/human_compact/trajectory/project_order.py:230–231 — unconditional container gate before model assessment.
  • Current local discovery: 17 components; one marked requiresContainer, the Harbor fixture service.
  • Repository: tooling/harbor/native-smoke/README.md — identifies the fixture as a compatibility test and documents Docker execution.
  • Repository: tooling/harbor/native-smoke/task/environment/docker-compose.yaml — fixture container command and network isolation.
  • Repository: package.json — Bun package manager, CLI default, and separate UI script.
